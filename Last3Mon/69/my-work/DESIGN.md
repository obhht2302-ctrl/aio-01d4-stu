## 1. 역할 카드 (Lab 01 예제 1)

| 칸 | 작성자 | 검토자 | 정리자 |
| --- | --- | --- | --- |
| 하는 일 (한 줄) | 요청과 제공된 사실만 사용해 읽기 쉬운 IT 공지 초안을 작성하고, 피드백이 있으면 초안을 수정한다. | 초안을 사실과 대조하여 누락·개인정보·길이·근거 없는 주장을 찾아 코드와 상세 의견으로 알린다. | 작성자와 검토자를 순서대로 호출하고, 검토 결과에 따라 게시 여부·경로·최종 공지를 정리한다. |
| 받는 것 | `request`, `facts`(필수), 수정 시 `previous_draft`, `feedback` | `facts`(필수), `draft`(필수) | `request`, `facts`(필수), `author` |
| 내놓는 것 | `draft` 하나를 담은 공지 초안 | `passed`, `codes`, `issues`를 담은 검토 결과 | `route`, `published`, `rounds`, `notice`, `codes` 등을 담은 최종 결과 |
| **하지 않는 일** | 자기 초안을 통과 처리하거나 검토 코드를 만들지 않고, 사실에 없는 약속·보상·날짜·연락처를 추가하지 않는다. | 초안을 직접 고쳐 쓰거나 게시하지 않고, 사실에 있는 내용을 표현만 다르다는 이유로 문제 삼지 않는다. | 공지 초안을 직접 작성하거나 직접 검토하지 않고, 작성자·검토자의 역할을 내부에서 다시 구현하지 않는다. |
| 잘했는지 아는 법 (테스트) | 날짜·시간을 사실에 적힌 그대로 포함하고, 제목이 있으며, 사실이 없으면 HTTP 400을 반환한다. | 정상 초안은 통과시키고, 각 문제 초안에는 기대한 코드만 반환하며, 입력이 없으면 HTTP 400을 반환한다. | 정상 초안은 게시하고, 한 번의 수정으로 해결되면 수정 후 게시하며, 계속 실패하거나 역할 호출에 문제가 생기면 담당자 확인으로 보낸다. |
| LLM이 필요한가 · 규칙으로 되나 | 자연스러운 공지 작성과 피드백 반영에는 LLM이 필요하다. 필수 입력 확인은 규칙으로 처리한다. | 날짜·시간 누락, 전화번호·메일, 600자 초과는 규칙으로 처리하고, 사실에 없는 약속·보상 판단만 LLM을 사용한다. | 역할 호출 순서, 재검토 횟수, 분기와 결과 조합은 규칙으로 처리하며 별도 LLM은 필요하지 않다. |
