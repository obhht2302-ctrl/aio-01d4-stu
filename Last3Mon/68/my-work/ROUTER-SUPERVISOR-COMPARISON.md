# 라우터와 Supervisor 비교

## 1. 비교 목적

같은 복합 요청을 규칙 기반 라우터(`my-assistant`)와 AI Supervisor(`my-supervisor`)에 각각 3회 보내 응답 시간과 결과 일관성을 비교했다.

측정일은 2026년 10월 20일이며, 측정 전에 `flow.py doctor`로 다음 항목이 모두 정상임을 확인했다.

- n8n과 OpenAI Credential
- 데이터 API의 터미널·n8n 내부 연결
- `it-agent`, `meeting-agent` 웹훅

## 2. 테스트 방법

두 워크플로우에 동일한 `requests/composite.json`을 순차적으로 3회씩 요청했다. 동시에 호출하지 않았으므로 두 방식이 서로의 실행 시간을 직접 방해하지 않도록 했다.

요청에는 다음 세 업무가 들어 있다.

1. `T-1002` 처리 상태 확인
2. 첨부된 회의록에서 할 일 정리
3. 프린터 출력 문제 해결

실행 명령은 다음과 같다.

```bash
uv run tools/flow.py call my-assistant requests/composite.json
uv run tools/flow.py call my-supervisor requests/composite.json
```

각 명령을 3회 반복하고 `flow.py`가 출력한 HTTP 전체 응답 시간을 기록했다. 이 시간에는 LLM 판단, Agent 웹훅 호출, 데이터 API 조회, 결과 작성 시간이 모두 포함된다.

## 3. 속도 측정 결과

| 실행 | 라우터 | Supervisor |
| ---: | ---: | ---: |
| 1회 | 10.4초 | 8.9초 |
| 2회 | 5.6초 | 10.0초 |
| 3회 | 5.4초 | 9.1초 |
| 평균 | **7.1초** | **9.3초** |
| 중앙값 | **5.6초** | **9.1초** |
| 최소–최대 | 5.4–10.4초 | 8.9–10.0초 |

이번 3회 측정에서 라우터는 Supervisor보다 평균 약 **2.2초**, 약 **24%** 짧은 시간이 걸렸다. 반대로 표현하면 Supervisor가 라우터보다 약 **31%** 오래 걸렸다.

라우터의 첫 실행은 10.4초로 이후 두 번보다 길었다. 모델이나 워크플로우의 첫 실행 준비 비용이 포함됐을 가능성이 있으므로, 3회의 평균만으로 일반적인 성능을 단정하면 안 된다. 준비 효과가 줄어든 라우터 2·3회의 평균은 5.5초였다.

## 4. 결과 일관성

### 라우터

세 번 모두 다음 결과가 같았다.

- 업무 수: 3개
- 업무 순서: 티켓 → 회의록 → 프린터
- 담당 Agent: `it-agent` → `meeting-agent` → `it-agent`
- 티켓 상태에 `처리 중` 포함
- 프린터 답변에 `전원`, `인쇄 대기열` 포함
- 회의록 행동 항목 4개 유지

회의록의 기한 표현이 `금요일`과 `금요일까지`처럼 조금 달라졌지만 `count`, `results`, `index`, `agent`, `route` 구조는 유지됐다.

### Supervisor

세 번 모두 다음 결과가 같았다.

- `agents_used`: `it-agent`, `meeting-agent`
- 티켓의 `처리 중` 상태 포함
- 회의록 담당자와 할 일 포함
- 프린터의 전원·네트워크·인쇄 대기열 안내 포함

최종 문장의 표현과 조사에는 작은 차이가 있었다. Supervisor는 Tool 결과를 다시 하나의 자연어 답변으로 작성하기 때문에 라우터보다 결과 모양이 덜 고정적이었다.

## 5. 속도 차이가 생기는 이유

라우터는 첫 LLM이 업무 목록을 만든 뒤 코드와 Switch가 분배한다. Agent 응답은 Set·Merge·Code 노드가 정해진 구조로 조합한다.

```text
LLM 업무 분리 → 코드 분배 → Agent 호출 → 코드 병합
```

Supervisor는 LLM이 요청을 해석하고, Tool을 선택하고, Tool 결과를 받은 뒤 최종 자연어 답변도 작성한다. 하나의 AI Agent 안에서 판단과 Tool 호출이 반복되므로 추가 LLM 처리 시간이 발생할 수 있다.

```text
Supervisor 판단 → Tool 선택·호출 반복 → Supervisor 최종 답변
```

## 6. 방식별 장단점

| 항목 | 라우터 | Supervisor |
| --- | --- | --- |
| 이번 평균 시간 | 7.1초 | 9.3초 |
| 분배 기준 | Switch의 명시적인 규칙 | LLM의 Tool 선택 |
| 결과 계약 | `count`, `results`, `reply`로 상세하고 고정적 | `reply`, `agents_used`로 단순함 |
| 실행 확인 | 업무별 분기와 결과를 쉽게 추적 | Tool 호출 기록을 확인해야 함 |
| 결과 일관성 | 비교적 높음 | 내용은 유지되지만 표현이 더 달라짐 |
| Agent 추가 | Switch·호출·결과 노드 수정 필요 | Tool과 설명을 추가하기 쉬움 |
| 적합한 상황 | 속도와 결과 형식이 중요한 업무 | 요청 종류가 다양하고 유연한 판단이 중요한 업무 |

## 7. 결론

이번 환경과 요청에서는 **라우터가 더 빠르고 결과 구조도 안정적**이었다. 업무 유형이 `it`, `meeting`, `other`처럼 명확하고 결과 계약을 엄격히 지켜야 한다면 라우터 방식이 적합하다.

Supervisor는 평균적으로 더 느렸지만 별도의 Switch와 병합 구조 없이 필요한 Agent를 유연하게 고를 수 있었다. 앞으로 Agent 종류가 자주 늘어나거나 요청을 사전에 고정된 유형으로 나누기 어렵다면 Supervisor 방식이 관리하기 쉬울 수 있다.

이번 결과는 각 방식 3회만 측정한 대략적인 비교다. 더 신뢰도 높은 결론이 필요하면 같은 환경에서 10회 이상 측정하고 첫 실행을 준비 실행으로 제외한 값도 함께 비교해야 한다.
