# Vibe Flow · n8n AI 워크플로우 학습 및 설계 명세

## 1. 문서 목적

이 문서는 지금까지 학습하고 구현한 n8n 기반 AI 워크플로우를 한곳에 정리한다. 단순히 n8n 노드를 연결하는 방법보다 다음 질문에 답하는 것을 목표로 한다.

- 업무를 어떤 단위로 나눌 것인가?
- AI, 규칙, Tool, Memory는 각각 어떤 일을 맡아야 하는가?
- 입력 오류와 외부 서비스 장애는 어떻게 처리할 것인가?
- 결과가 올바른지 무엇으로 검증할 것인가?
- 완성된 워크플로우를 어떻게 재사용하고 안전하게 변경할 것인가?

핵심 목표는 AI에게 모든 판단을 맡기는 것이 아니다. **AI가 잘하는 자연어 이해와 생성을 규칙, 데이터, 검증, 역할 분리로 통제하여 반복 가능한 업무 절차로 만드는 것**이다.

---

## 2. n8n 워크플로우란

n8n 워크플로우는 입력을 받아 여러 노드가 정해진 순서와 조건에 따라 처리하고 결과를 반환하는 자동화 흐름이다.

가장 기본적인 구조는 다음과 같다.

```text
Trigger → Condition → Action → Result
```

| 구성 | 역할 | n8n 예시 |
| --- | --- | --- |
| Trigger | 워크플로우가 시작되는 사건 | Webhook, Schedule, Manual Trigger |
| Condition | 입력이나 중간 결과에 따른 분기 | IF, Switch, Code |
| Action | 조회, 생성, 변환, 저장 등 실제 처리 | AI Agent, HTTP Request, Set, Code |
| Result | 호출자에게 처리 결과 반환 | Respond to Webhook |

AI가 포함된 워크플로우에서도 이 기본 구조는 바뀌지 않는다. AI는 워크플로우 전체가 아니라 의미 이해가 필요한 일부 단계에 배치한다.

## 3. 구성 요소별 책임

### 3.1 LLM과 AI Agent

LLM은 자연어의 의미를 이해하거나 새로운 문장을 만들어야 하는 일에 사용한다.

- 문의 분류
- 회의록 요약
- 할 일 추출
- 복합 요청 분해
- 공지문 초안 작성
- 제공된 사실과 문장의 의미 비교

AI Agent는 LLM에 Tool 선택 능력을 더한 형태다. 요청에 따라 FAQ 검색이나 티켓 조회처럼 필요한 Tool을 스스로 고를 수 있다.

다만 빈 값 검사, 문자열 길이, 개인정보 패턴, 실행 횟수 같은 확정적인 조건에는 LLM을 사용하지 않는다.

### 3.2 규칙과 일반 노드

규칙은 같은 입력에 항상 같은 판단이 나와야 하는 일에 사용한다.

- 필수 입력 확인
- HTTP 상태 코드 결정
- 문자열 길이 검사
- JSON 파싱과 필드 정규화
- 개인정보 패턴 검사
- 업무 종류별 라우팅
- 재시도 횟수 제한
- 결과 배열 취합

규칙으로 해결할 수 있는 일을 먼저 처리하면 비용과 응답 시간을 줄이고 결과를 예측하기 쉬워진다.

### 3.3 Tool과 외부 데이터

Tool은 AI가 알 수 없는 실제 정보나 최신 정보를 가져오거나 외부 시스템에서 작업할 때 사용한다.

- 사내 FAQ 검색
- 티켓 처리 상태 조회
- 캘린더 일정 조회·등록
- 데이터베이스 읽기·쓰기
- 다른 Agent의 Webhook 호출

AI는 Tool을 선택할 수 있지만, 사용자 인증과 접근 권한은 API나 인증 시스템이 강제해야 한다. 사용자가 자연어로 주장한 이름을 신원 정보로 그대로 믿으면 안 된다.

### 3.4 Memory

Memory는 이전 대화나 처리 상태를 다음 실행에서 다시 사용할 때 필요하다.

- 사용자 선호 저장
- 이전 문의 이력 조회
- 장기 작업의 진행 상태 유지
- 이전 추천 결과를 이용한 개인화

현재 요청을 처리하는 데만 필요한 값은 워크플로우의 중간 데이터로 전달하고, 다음 실행에도 필요한 값만 Memory에 저장한다.

### 3.5 사람

사람은 다음 책임을 가진다.

- 원하는 최종 결과 정의
- 허용할 자동화 범위 결정
- 테스트와 합격 기준 작성
- 개인정보, 게시, 결제 등 위험한 작업 승인
- 실패 결과와 실행 기록 검토

## 4. 학습한 워크플로우의 발전 과정

### 4.1 기본 구조: LLM·Tool·Memory

첫 단계에서는 AI 워크플로우를 다음과 같이 분해했다.

```text
입력 → 판단 → 정보 조회 → 처리 → 검증 → 출력
```

LLM 단독 응답, Tool의 근거를 사용한 응답, 사용자 정보 저장, Memory를 이용한 개인화 등을 통해 각 구성 요소의 책임을 구분했다.

### 4.2 Trigger·Condition·Action

정상 입력만 처리하는 흐름에서 벗어나 빈 입력, 예상하지 못한 분류, 검색 결과 없음, 외부 API 실패까지 처리하도록 확장했다.

모든 분기에는 끝나는 경로와 명확한 결과가 있어야 한다.

### 4.3 결과 우선 설계

노드를 만들기 전에 먼저 다음을 정했다.

1. 사용자가 받을 최종 결과
2. 결과의 JSON 구조
3. 필수 입력과 선택 입력
4. 정상·예외·실패 사례
5. 결과를 확인할 테스트

그 후 결과를 만들기 위해 필요한 노드를 역으로 설계했다. 이 방식은 구현 중 요구사항이 계속 바뀌거나 그럴듯한 문장만 남는 문제를 줄여 준다.

### 4.4 Agent와 Tool

AI Agent가 사용자의 요청에 맞춰 FAQ 검색과 티켓 조회 Tool을 선택하도록 만들었다. Tool의 실제 결과를 근거로 답하고, 근거가 부족하면 추측하지 않고 담당자 연결 경로로 보냈다.

### 4.5 Multi-Agent 라우팅

하나의 요청에 여러 업무가 섞였을 때 요청을 작은 업무로 분리한 뒤 담당 Agent로 전달했다.

```text
복합 요청
→ 업무 분해
→ 종류별 라우팅
→ 담당 Agent 호출
→ 결과 취합
→ 통합 응답
```

이 구조의 목적은 Agent 수를 늘리는 것이 아니라 책임과 장애 범위를 분리하는 것이다.

### 4.6 역할 기반 협업

서로 다른 업무를 분배하는 것에서 더 나아가, 하나의 업무도 작성자와 검토자처럼 역할별로 분리했다.

```text
작성 → 검토 → 통과 여부
              ├─ 통과: 게시 준비
              └─ 실패: 한 번 수정 → 재검토
```

작성자는 제공된 사실로 초안을 만들고, 검토자는 누락·개인정보·길이·근거 없는 내용을 검사한다. 워크플로우는 수정 횟수와 게시 여부를 결정한다.

### 4.7 템플릿화·모듈화·버전 관리

비슷한 워크플로우를 종류별로 복사하는 대신 다음과 같이 재구성했다.

- 다른 값: 설정 표로 이동
- 여러 곳에서 쓰는 같은 처리: Sub-workflow 모듈로 분리
- 하위 호환 변경: 같은 모듈 ID 유지
- 결과 계약이 깨지는 변경: 새 버전과 새 ID 사용
- 변경 후: 모듈을 사용하는 모든 워크플로우의 테스트 실행

## 5. 실제 사례 1 · 회의록에서 할 일 추출

### 목적

회의 제목과 회의록을 받아 요약과 할 일을 구조화된 JSON으로 반환한다.

### 처리 흐름

```text
Meeting Webhook
→ 회의록 존재 여부 확인
→ 요약과 할 일 추출을 병렬 실행
→ 할 일 JSON 파싱
→ 항목별 담당자·마감일 확인
→ 결과 취합
→ 보고서 반환
```

### 주요 규칙

- 회의록이 비어 있으면 HTTP 400을 반환한다.
- 원문에 없는 담당자나 마감일을 추측하지 않는다.
- 마감일이 없으면 `null` 또는 확인 필요 상태로 표시한다.
- 할 일이 없더라도 정상적인 빈 결과를 반환한다.
- 결과는 후속 시스템이 사용할 수 있는 배열 형태로 만든다.

### 결과 예시

```json
{
  "summary": "신규 서비스 출시 준비 상황을 점검했다.",
  "actions": [
    {
      "task": "발표 자료 초안 작성",
      "owner": "김민지",
      "due_date": null,
      "needs_confirmation": true
    }
  ]
}
```

### 배운 점

자연어 요약만으로는 자동화하기 어렵다. 후속 저장·알림·분배가 가능하도록 결과를 구조화해야 한다.

## 6. 실제 사례 2 · 사내 IT 문의 Agent

### 목적

IT 문의를 받고 Agent가 FAQ 또는 티켓 조회 Tool을 선택해 근거 있는 답변을 반환한다.

### 처리 흐름

```text
IT Question Webhook
→ 질문 존재 여부 확인
→ IT Agent
   ├─ FAQ 검색 Tool
   └─ 티켓 조회 Tool
→ 답변 검증
→ 자동 답변 또는 담당자 연결
```

### 주요 규칙

- 질문이 없으면 HTTP 400을 반환한다.
- FAQ 답변은 검색 결과를 근거로 작성한다.
- 티켓은 인증된 요청자 본인의 건만 조회한다.
- 근거가 없거나 답변 검증에 실패하면 담당자에게 연결한다.
- 사용한 Tool과 출처를 결과에 남긴다.

### 결과 예시

```json
{
  "route": "auto_answer",
  "answer": "VPN 클라이언트의 인증서를 갱신한 뒤 다시 연결해 주세요.",
  "tools_used": ["search_faq"],
  "sources": ["FAQ-VPN-003"]
}
```

### 배운 점

AI가 답을 알고 있다고 가정하지 않고 실제 데이터에 연결해야 한다. 특히 권한은 AI 프롬프트가 아니라 시스템이 강제해야 한다.

## 7. 실제 사례 3 · 복합 요청을 처리하는 사내 업무 도우미

### 목적

한 문장에 IT 문의, 회의록 처리, 기타 요청이 섞여 있어도 각각 분리해 담당 Agent로 보내고 결과를 하나로 합친다.

### 처리 흐름

```text
Assistant Webhook
→ LLM이 요청을 업무 목록으로 분해
→ JSON 파싱과 누락 입력 확인
→ 업무별 항목 생성
→ Switch로 종류별 라우팅
   ├─ IT → IT Agent
   ├─ Meeting → Meeting Agent
   └─ Other → 담당자 연결
→ 결과 취합
→ 원래 요청 순서대로 통합 응답
```

### 입력 예시

> T-1002 상태를 확인하고, 첨부한 회의록에서 할 일도 정리해 주세요. 프린터 출력 문제도 해결하고 싶습니다.

### 결과 계약 예시

```json
{
  "count": 3,
  "results": [
    {
      "index": 0,
      "type": "it",
      "agent": "it-agent",
      "route": "auto_answer",
      "answer": "T-1002는 처리 중입니다."
    },
    {
      "index": 1,
      "type": "meeting",
      "agent": "meeting-agent",
      "route": "completed",
      "actions": []
    },
    {
      "index": 2,
      "type": "it",
      "agent": "it-agent",
      "route": "auto_answer",
      "answer": "전원과 인쇄 대기열을 먼저 확인해 주세요."
    }
  ],
  "reply": "세 가지 요청의 처리 결과입니다."
}
```

### 라우터와 Supervisor 비교 결과

동일한 복합 요청을 각각 3회 실행했을 때 다음 결과를 얻었다.

| 항목 | 규칙 기반 라우터 | AI Supervisor |
| --- | ---: | ---: |
| 평균 응답 시간 | 7.1초 | 9.3초 |
| 결과 형식 | 상세하고 안정적 | 단순하지만 표현 변화가 있음 |
| 분배 방법 | 명시적인 Switch | LLM의 Tool 선택 |
| 추적 용이성 | 업무별 경로 확인이 쉬움 | Tool 호출 기록 확인 필요 |
| 적합한 경우 | 종류와 결과 계약이 명확함 | 종류가 자주 늘고 판단이 유동적임 |

이번 사례에서는 라우터가 평균 약 2.2초 빨랐고 결과 구조도 더 일관적이었다. 다만 측정 횟수가 3회뿐이므로 일반적인 성능 결론이 아니라 해당 환경의 참고 결과로 사용한다.

### 배운 점

업무 종류가 명확하면 명시적인 라우터가 단순하고 안정적이다. Supervisor는 고정된 분류로 나누기 어려운 요청에 선택적으로 사용한다.

## 8. 실제 사례 4 · 작성자와 검토자가 협업하는 공지 팀

### 목적

제공된 사실을 이용해 IT 공지를 작성하고, 별도의 검토자가 안전성과 정확성을 검사한 뒤 게시 가능 여부를 결정한다.

### 역할 계약

| 역할 | 입력 | 출력 | 하지 않는 일 |
| --- | --- | --- | --- |
| 작성자 | `request`, `facts`, 선택적으로 `previous_draft`, `feedback` | `draft` | 자기 초안을 통과 처리하거나 없는 사실 추가 |
| 검토자 | `facts`, `draft` | `passed`, `codes`, `issues` | 초안을 직접 수정하거나 게시 |
| 워크플로우 | 작성·검토 결과 | 게시 여부와 최종 결과 | 역할의 판단을 내부에 중복 구현 |

### 검토 항목

- 필수 날짜와 시간 누락
- 전화번호와 이메일 등 개인정보 포함
- 허용 길이 초과
- 사실에 없는 약속, 보상, 연락처 추가
- 프롬프트 인젝션 성격의 지시문 포함

### 실패 정책

- 첫 검토 실패 시 피드백을 전달해 한 번만 수정한다.
- 두 번째 검토도 실패하면 담당자 확인으로 보낸다.
- 검토자가 응답하지 않으면 게시하지 않는다.
- 안전 검토는 `fail-closed` 정책을 사용한다.

### 결과 예시

```json
{
  "route": "수정 후 게시 가능",
  "published": true,
  "rounds": 2,
  "notice": "[점검 안내] 10월 23일 22:00부터 메일 서버를 점검합니다.",
  "codes": [],
  "first_codes": ["personal_info"],
  "steps": ["writer", "reviewer", "writer", "reviewer"]
}
```

### 배운 점

한 Agent가 작성과 검토를 모두 수행하게 하지 않고 역할을 분리하면 오류 위치를 찾고 각 역할을 독립적으로 테스트하기 쉽다.

## 9. 실제 사례 5 · 공지 키트와 규칙 검사 모듈

### 목적

점검·보안·교육 공지의 중복 워크플로우를 하나의 공지 키트로 통합하고 공통 검사를 재사용 가능한 모듈로 분리한다.

### 설정 표로 이동할 값

| 종류 | 머리말 | 최대 길이 | 필수 문장 | 작성 주의사항 |
| --- | --- | ---: | --- | --- |
| maintenance | 점검 안내 | 600 | 없음 | 작업 시간과 영향을 정확히 표시 |
| security | 보안 안내 | 500 | IT팀은 절대 비밀번호를 묻지 않습니다. | 비밀번호 입력을 유도하지 않음 |
| training | 교육 안내 | 800 | 신청은 IT 포털에서 할 수 있습니다. | 신청 방법과 일정을 포함 |

설정 표에 없는 종류는 기본값으로 조용히 처리하지 않고 HTTP 400과 허용 목록을 반환한다.

### 규칙 검사 모듈 계약

```json
{
  "input": {
    "facts": "string",
    "draft": "string",
    "max_length": 600,
    "required_phrases": [],
    "allowed_domains": ["intra.example.com"]
  },
  "output": {
    "passed": true,
    "codes": [],
    "issues": []
  }
}
```

같은 모듈을 공지 키트와 SMS 워크플로우가 함께 사용한다. SMS처럼 사용처마다 다른 최대 길이는 모듈 내부 조건으로 넣지 않고 입력값으로 전달한다.

### 버전 관리

- 선택 입력 추가처럼 기존 사용처가 깨지지 않는 변경은 같은 모듈 ID를 유지할 수 있다.
- `codes`를 `blocking`, `warnings`로 바꾸는 것처럼 출력 계약이 달라지는 변경은 새 ID의 v2 모듈로 만든다.
- 사용하는 워크플로우를 영향 표에 기록하고 모듈 변경 후 관련 테스트를 모두 다시 실행한다.

### 배운 점

복사는 만들 때는 빠르지만 고칠 때 비싸다. 여러 곳에서 바뀌는 값은 설정으로, 여러 곳에서 쓰는 처리는 모듈로 분리해야 한다.

## 10. 개인 활용 사례 · 개인 인박스 정리기

### 목표

사용자가 자유롭게 적은 메시지를 일정, 할 일, 지출, 메모로 분리하고 저장 전에 확인할 수 있도록 한다.

### 입력 예시

> 내일 오후 3시에 치과 예약. 오늘 교재비로 35,000원 썼어. 금요일까지 발표 자료를 만들고 멀티 에이전트와 라우터 차이도 메모해 줘.

### 권장 처리 흐름

```text
Personal Inbox Webhook
→ 입력·사용자·시간대 확인
→ LLM이 항목 목록으로 분해
→ JSON 파싱과 날짜·금액 검증
→ 종류별 라우팅
   ├─ 일정 후보
   ├─ 할 일 후보
   ├─ 지출 후보
   ├─ 메모 후보
   └─ 정보 부족 항목
→ 전체 미리보기 반환
→ 사용자 승인
→ 승인된 항목만 외부 시스템에 저장
→ 성공·실패 결과와 실행 기록 반환
```

### 미리보기 결과 예시

```json
{
  "status": "confirmation_required",
  "items": [
    {
      "type": "calendar",
      "title": "치과 예약",
      "starts_at": "2026-10-23T15:00:00+09:00"
    },
    {
      "type": "expense",
      "category": "교육",
      "amount": 35000,
      "description": "교재비"
    },
    {
      "type": "task",
      "title": "발표 자료 만들기",
      "due_date": "2026-10-23"
    },
    {
      "type": "note",
      "title": "멀티 에이전트와 라우터의 차이",
      "content": null,
      "needs_input": true
    }
  ]
}
```

### 안전 원칙

- 모호한 날짜나 금액을 추측해서 저장하지 않는다.
- 저장 전 사용자에게 최종 미리보기를 보여 준다.
- 인증된 사용자 ID와 시간대를 사용한다.
- 한 종류의 저장이 실패해도 다른 항목의 결과는 보존한다.
- 외부 시스템에 보낸 값과 받은 결과를 실행 기록에 남긴다.
- 초기 버전은 Supervisor보다 종류가 명확한 규칙 기반 라우터를 사용한다.

## 11. 공통 설계 원칙

### 11.1 결과를 먼저 정한다

워크플로우를 만들기 전에 성공 결과, 실패 결과, JSON 필드와 HTTP 상태 코드를 정한다.

### 11.2 규칙과 AI를 분리한다

의미 판단과 문장 생성은 AI가 담당하고, 필수값·길이·형식·권한·반복 횟수는 규칙과 시스템이 담당한다.

### 11.3 AI가 사실을 만들지 않게 한다

최신 정보와 사내 정보는 Tool에서 가져온다. 정보가 없으면 `null`, 확인 필요 또는 담당자 연결을 반환한다.

### 11.4 입출력 계약을 명시한다

각 Agent와 모듈은 받는 값, 내놓는 값, 하지 않는 일, 실패 형식을 문서화한다.

### 11.5 성공 경로와 실패 경로를 함께 만든다

빈 입력, 알 수 없는 종류, JSON 파싱 실패, Tool 장애, Agent 무응답, 검토 실패까지 종료 경로가 있어야 한다.

### 11.6 위험도에 따라 실패 정책을 선택한다

- `fail-open`: 일부 Agent가 실패해도 안전한 나머지 결과를 제공
- `fail-closed`: 검토나 권한 확인에 실패하면 게시·저장하지 않음

### 11.7 관찰 가능한 결과를 남긴다

최종 답변뿐 아니라 사용한 Tool, 처리 단계, 라우팅 결과, 검토 코드, 실행 시간과 실패 원인을 남긴다.

### 11.8 작은 단위로 시험한 뒤 연결한다

Agent, Tool, Sub-workflow를 각각 시험한 후 전체 워크플로우를 통합 테스트한다.

```text

```

## 13. 테스트 기준

새 워크플로우에는 최소한 다음 범주의 테스트가 필요하다.

### 정상 입력

- 대표 입력이 기대한 상태 코드와 결과 구조를 반환하는가?
- 필수 내용이 결과에 포함되는가?
- 항목 순서와 개수가 유지되는가?

### 경계 입력

- 빈 문자열과 공백만 있는 문자열
- 선택 필드 누락
- 매우 긴 입력
- 알 수 없는 종류
- 날짜·금액 등 일부 정보 부족

### 안전 입력

- 개인정보 포함
- 사실에 없는 내용을 추가하라는 요청
- 입력 데이터 안에 포함된 명령문
- 다른 사용자의 데이터 조회 시도

### 장애 입력

- Tool 응답 없음
- Agent Webhook 중단
- 잘못된 JSON 반환
- 일부 작업만 실패
- 검토자 무응답

### 반복 검증

LLM 결과는 실행마다 표현이 달라질 수 있으므로 중요한 케이스는 여러 번 실행한다. 문장 전체 일치보다 상태, 필드, 필수 내용, 금지 내용과 같은 관찰 가능한 조건을 검사한다.

## 14. 완료 조건

워크플로우는 다음 조건을 만족할 때 완료로 본다.

- 입력과 출력 계약이 문서화되어 있다.
- 정상·예외·실패 경로가 모두 종료된다.
- AI가 없는 사실이나 권한을 만들지 않는다.
- 개인정보와 위험한 외부 작업에 안전장치가 있다.
- 각 Agent와 모듈을 독립적으로 테스트할 수 있다.
- 전체 테스트가 통과하고 실행 보고서가 남는다.
- 사용한 Tool과 주요 처리 단계를 추적할 수 있다.
- 설정값과 공통 로직이 불필요하게 복사되어 있지 않다.
- 변경 시 영향을 받는 워크플로우와 테스트를 알 수 있다.

## 15. 핵심 요약

```text
1. 결과를 먼저 정의한다.
2. 입력과 출력의 계약을 정한다.
3. 업무를 작은 단계와 역할로 나눈다.
4. 규칙으로 가능한 일은 규칙으로 처리한다.
5. 의미 이해와 문장 생성에만 AI를 사용한다.
6. 사실과 최신 정보는 Tool로 가져온다.
7. 인증과 권한은 시스템이 강제한다.
8. 성공뿐 아니라 예외와 실패 경로도 만든다.
9. 각 부분을 따로 시험한 뒤 전체를 연결한다.
10. 공통 기능은 모듈화하고 계약 변경은 버전으로 관리한다.
```

n8n AI 워크플로우의 목적은 AI 사용량을 늘리는 것이 아니다. **AI의 불확실성을 통제하면서 실제 업무를 안전하고 반복 가능하며 검증 가능한 형태로 자동화하는 것**이다.
