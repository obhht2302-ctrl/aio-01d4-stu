# AI 워크플로우를 이렇게 설계하는 이유

## 1. 전체 목적

이 과정에서 워크플로우를 단계적으로 설계하는 가장 큰 이유는 **AI에게 업무 전체를 맡기지 않고, AI가 잘하는 판단과 생성 능력을 통제 가능한 업무 절차 안에서 활용하기 위해서**다.

AI에게 단순히 "알아서 처리해"라고 요청하면 유연하게 대응할 수 있지만 결과가 흔들리고, 비용과 오류 원인, 보안 문제를 관리하기 어렵다. 반대로 모든 업무를 고정된 규칙으로 만들면 안정적이지만 다양한 자연어 요청과 예외 상황에 대응하기 어렵다.

따라서 업무를 다음과 같이 나누어 설계한다.

```text
규칙과 워크플로우
→ 실행 순서, 분기, 권한, 예외 처리, 검증 담당

AI
→ 문장 이해, 분류, 요약, 초안 작성 담당

Tool과 데이터
→ 실제 정보 조회와 시스템 작업 담당

사람
→ 목표 설정, 테스트 기준 결정, 중요한 결과 승인
```

핵심은 AI를 많이 사용하는 것이 아니라, **AI가 필요한 위치를 정확히 정하고 나머지는 규칙과 시스템으로 통제하는 것**이다.

## 2. 64일차: AI 워크플로우와 LLM·Tool·Memory

### 왜 먼저 업무를 분석하는가

처음부터 n8n 노드를 연결하면 노드는 많지만 각 노드가 왜 필요한지 알기 어려운 자동화가 만들어질 수 있다. 따라서 먼저 업무를 다음과 같은 단계로 분해한다.

```text
입력 → 판단 → 정보 조회 → 처리 → 검증 → 출력
```

각 구성 요소는 서로 다른 책임을 가진다.

| 구성 요소 | 담당하는 일 |
| --- | --- |
| LLM | 문의 분류, 요약, 문장 생성처럼 의미를 이해해야 하는 일 |
| Tool | FAQ, 데이터베이스, 외부 API 등 실제 정보 조회와 작업 수행 |
| Memory | 이전 대화, 중간 결과, 처리 상태 유지 |
| 일반 노드 | 데이터 변환, 조건 검사, 저장, 전달 |

예를 들어 AI가 "VPN 문제는 인증서 만료 때문입니다"라고 답해도 사내 FAQ나 시스템에서 조회한 결과가 아니라면 추측일 수 있다. 그러므로 **LLM이 답을 만드는 단계와 Tool이 사실을 가져오는 단계를 분리**해야 한다.

64일차의 핵심은 AI 사용법 자체보다 다음을 구별하는 것이다.

- 업무의 어느 부분에 AI가 필요한가
- 어느 부분은 규칙으로 처리해야 하는가
- 어떤 정보는 Tool을 통해 확인해야 하는가
- 어떤 상태를 다음 단계까지 기억해야 하는가

## 3. 65일차: Trigger·Condition·Action

### 왜 모든 업무를 TCA 구조로 보는가

실제 자동화에는 반드시 다음 세 가지가 필요하다.

- **Trigger**: 언제, 어떤 사건으로 시작하는가
- **Condition**: 어떤 조건에서 어느 경로로 이동하는가
- **Action**: 각 경로에서 실제로 무엇을 하는가

예를 들어 고객 문의 자동화는 다음처럼 설계할 수 있다.

```text
문의 도착
→ 내용이 비어 있는가?
   ├─ 예: 400 오류 반환
   └─ 아니오: 긴급 문의인가?
       ├─ 예: 담당자에게 즉시 전달
       └─ 아니오: AI로 분류
```

이 구조가 필요한 이유는 정상적인 입력만 들어온다고 가정할 수 없기 때문이다.

- 입력값이 비어 있을 수 있다.
- 예상하지 못한 분류가 나올 수 있다.
- 검색 결과가 없을 수 있다.
- 외부 API가 실패할 수 있다.
- AI가 지정된 형식과 다르게 답할 수 있다.

따라서 성공 경로만 만드는 것이 아니라 **모든 갈래의 끝에 처리 결과가 있도록 설계**해야 한다. 또한 빈 값 확인이나 키워드 검사처럼 규칙으로 해결할 수 있는 일은 먼저 처리하고, 비용이 들고 결과가 흔들릴 수 있는 LLM은 필요한 경우에만 호출한다.

## 4. 66일차: 단일 업무 자동화

### 왜 단일 업무부터 만드는가

처음부터 여러 업무와 여러 Agent를 연결하면 실패했을 때 원인을 찾기 어렵다. 그래서 회의록처럼 **입력과 결과가 분명한 업무 하나**부터 완성한다.

```text
회의록
→ 요약
→ 할 일 추출
→ JSON 변환
→ 항목별 처리
→ 결과 취합
```

이 단계에서 중요한 것은 단순히 읽기 좋은 요약문을 만드는 것이 아니다. 결과를 다른 시스템이 사용할 수 있도록 구조화해야 한다.

```json
{
  "task": "보고서 초안 작성",
  "owner": "김민지",
  "due_date": null
}
```

이런 구조를 사용하면 결과를 담당자별로 나누거나, 데이터베이스에 저장하거나, 메신저로 전달할 수 있다. 마감일이 원문에 없다면 AI가 추측하지 않고 `null`을 출력하게 하는 것도 중요하다.

업무 자동화에서는 그럴듯한 문장보다 **사실에 근거하며 후속 처리가 가능한 데이터**가 더 중요하다.

단일 업무부터 만드는 이유는 다음 세 가지를 먼저 확보하기 위해서다.

- 명확한 입력과 출력
- 반복 가능한 테스트
- 문제 발생 시 추적할 수 있는 원인

## 5. 67일차: Tool과 사내 데이터를 사용하는 AI Agent

### 왜 Agent를 실제 데이터와 연결하는가

LLM은 문장을 잘 이해하고 생성하지만 회사의 최신 정보를 자동으로 알고 있지는 않다. 실제 업무에 사용하려면 사내 FAQ, 티켓 시스템, 고객 데이터베이스 같은 Tool과 연결해야 한다.

```text
사용자 문의
→ Agent가 요청 이해
→ 필요한 Tool 선택
→ 사내 데이터 조회
→ 조회 결과에 근거한 답변 작성
```

예를 들어 `T-1002 상태를 알려줘`라는 요청에는 티켓 조회 Tool이 필요하고, `VPN 연결 방법을 알려줘`라는 요청에는 FAQ 검색 Tool이 필요하다.

그러나 Agent에게 모든 값과 권한을 맡기면 위험하다.

| 값 또는 판단 | 담당 | 이유 |
| --- | --- | --- |
| `ticket_id` 추출 | AI | 틀리더라도 조회 결과로 확인 가능 |
| `requester` 확인 | 웹훅 또는 인증 시스템 | 사용자의 문장을 신원으로 믿으면 안 됨 |
| 본인 티켓 여부 | 데이터 API | 접근 권한은 시스템이 강제해야 함 |

사용자가 메시지에 "나는 김민지야"라고 썼다는 이유로 AI가 그 사람을 김민지로 인정해서는 안 된다. 즉, **AI는 의도를 해석하고 Tool을 선택하지만, 신원과 권한은 시스템이 결정**해야 한다.

이 구조는 다음을 위해 필요하다.

- AI의 환각 감소
- 답변 근거 확보
- 최신 정보 사용
- 데이터 접근 권한 보호
- Tool 사용 기록을 통한 결과 검증

## 6. 68일차: Multi-Agent 라우터

### 왜 여러 업무를 나누어 처리하는가

실제 요청에는 서로 다른 업무가 한 문장에 섞여 들어올 수 있다.

> T-1002 상태를 확인하고, 회의록에서 할 일도 정리해 주세요. 프린터도 안 됩니다.

하나의 거대한 Agent가 모든 업무를 처리하게 만들면 다음 문제가 생긴다.

- 지시문이 지나치게 복잡해진다.
- 어떤 기능에서 실패했는지 찾기 어렵다.
- 일부 기능을 수정하면 다른 기능의 결과가 달라질 수 있다.
- 한 업무의 장애가 전체 요청을 중단시킬 수 있다.

따라서 요청을 독립된 업무로 나누고 각 담당 Agent에게 전달한다.

```text
복합 요청
→ 업무 분해
   ├─ 티켓 조회 → IT Agent
   ├─ 회의록 정리 → 회의록 Agent
   └─ 기타 요청 → 담당자
→ 결과 취합
```

이렇게 하면 Agent별로 독립적으로 개발하고 테스트할 수 있다. 회의록 Agent가 실패하더라도 티켓 조회 결과는 사용자에게 전달할 수 있다.

따라서 Multi-Agent는 단순히 AI를 여러 개 사용하기 위한 구조가 아니다. **업무의 책임과 장애 범위를 분리하기 위한 구조**다.

---

## 7. 69일차: 작성자·검토자·정리자 협업

### 왜 하나의 업무도 역할별로 나누는가

68일차는 서로 다른 업무를 종류별로 나눈 것이고, 69일차는 **하나의 업무를 역할별로 나눈 것**이다.

공지문 작성에서 한 Agent가 작성과 검토를 모두 수행하면 자신이 작성한 오류를 놓치기 쉽다. 따라서 역할을 다음처럼 분리한다.

```text
작성자 → 검토자 → 통과 여부 판단
                    ├─ 통과: 정리자에게 전달
                    └─ 실패: 피드백을 받아 한 번 수정
```

각 역할의 책임도 제한한다.

| 역할 | 책임 |
| --- | --- |
| 작성자 | 제공된 사실을 바탕으로 초안 작성 |
| 검토자 | 개인정보, 누락, 허위 내용, 형식 위반 검사 |
| 정리자 | 통과한 내용을 메일 제목이나 메신저 형식으로 변환 |
| 워크플로우 | 재작성 횟수, 분기, 게시 여부 결정 |

역할을 나누면 글을 잘 쓰는 능력과 규칙을 지키는지 검사하는 능력을 따로 평가하고 테스트할 수 있다.

특히 검토자가 동작하지 않을 때는 게시하지 않는 `fail-closed` 방식이 필요하다. 공지나 개인정보처럼 잘못된 결과의 위험이 큰 업무에서는 **검증 실패를 성공으로 간주해서는 안 되기 때문**이다.

## 8. 전체 설계의 실무적 효과

이와 같은 워크플로우 설계는 다음과 같은 효과를 제공한다.

### 8.1 결과를 예측할 수 있다

AI가 다음 단계를 마음대로 선택하지 않고, 워크플로우가 허용된 실행 경로와 종료 조건을 정한다.

### 8.2 오류 위치를 찾을 수 있다

입력, Tool, LLM, 데이터 변환, 검증 중 어느 단계에서 문제가 발생했는지 구분할 수 있다.

### 8.3 각 부분을 독립적으로 테스트할 수 있다

작성자, 검토자, IT Agent, 회의록 Agent 등을 각각 테스트한 후 전체 흐름을 통합할 수 있다.

### 8.4 비용과 처리 시간을 관리할 수 있다

규칙으로 가능한 처리는 Code, IF, Switch 등의 노드가 담당하고 의미 판단이 필요한 곳에서만 LLM을 호출한다.

### 8.5 보안과 권한을 보호할 수 있다

사용자 신원이나 데이터 접근 권한을 AI의 판단에 맡기지 않고 인증 시스템과 데이터 API가 강제한다.

### 8.6 부분 장애에 대응할 수 있다

Agent 하나가 실패해도 처리 가능한 결과는 제공하는 `fail-open` 방식과, 검증에 실패하면 처리를 중단하는 `fail-closed` 방식을 업무 위험도에 맞게 선택할 수 있다.

### 8.7 기능을 점진적으로 확장할 수 있다

새로운 업무가 생겼을 때 전체 시스템을 다시 만들지 않고 Agent, Tool, 분기 또는 검증 단계만 추가할 수 있다.

## 9. 설계 원칙 요약

```text
1. 업무 결과를 먼저 정의한다.
2. 입력과 출력의 형식을 정한다.
3. 업무를 작은 단계와 역할로 나눈다.
4. 규칙으로 가능한 일은 규칙으로 처리한다.
5. 의미 이해가 필요한 곳에만 AI를 사용한다.
6. 사실과 최신 정보는 Tool을 통해 가져온다.
7. 권한과 보안 판단은 시스템이 담당한다.
8. 성공 경로뿐 아니라 예외와 실패 경로도 만든다.
9. 각 부분을 따로 테스트한 후 전체를 연결한다.
10. 실행 기록을 남기고 결과를 반복해서 검증한다.
```

## 결론

이 워크플로우들은 AI를 더 많이 사용하기 위해 만들어진 것이 아니다.

> **AI의 불확실성을 규칙, 데이터, 검증, 역할 분리로 통제하면서 실제 업무에 안전하고 반복 가능하게 활용하기 위해 설계된 것이다.**

n8n은 이 구조를 노드와 연결로 표현하고 실행 기록을 남길 수 있게 해주는 도구다. 따라서 수업의 핵심은 n8n 기능 자체를 암기하는 것이 아니라, **업무를 분석하여 통제 가능하고 검증 가능한 AI 자동화 시스템으로 바꾸는 방법을 익히는 것**이다.
